# Auto-update — design (2026-09-25, reviewed)

QuickTerm is distributed as a Developer ID-signed, notarized DMG on GitHub Releases. This spec adds
in-app updating: a scheduled check, an indicator in the status bar when a newer release exists, a
window with the release notes and an install button, and an optional automatic
download-and-install-on-quit mode. The updater is Sparkle 2 driven by a custom user driver ported
from upstream Ghostty's `Features/Update`, so the whole UI is QuickTerm's own.

Decisions taken with the user (2026-09-25):

- Approach **A**: Sparkle 2 + a custom `SPUUserDriver` ported from Ghostty; no Sparkle windows
  while the app runs.
- Automatic install means Sparkle's semantics: download silently, **install on quit**, show a
  "quit or restart to finish" indicator meanwhile; no forced relaunch.
- Defaults: `check = true`, `install = false`.
- Release notes come in both languages: `docs/releases/v<ver>.md` (English, as today) and
  `docs/releases/v<ver>.zh-CN.md` (Simplified Chinese, new), both required from the next release.
- No major/minor version bump for this feature; the next release is the usual third-level bump.
- The EdDSA private key is generated by the user on the release Mac (`generate_keys`), never
  handled by the assistant; only the public key enters the repository.

This revision incorporates a three-lens review (Sparkle semantics, codebase fit, pipeline and
security); the Sparkle facts below were checked against Sparkle 2.x sources and the vendored
Ghostty port.

## 1. Goals and non-goals

Goals

1. `[updates] check = true|false` — check the feed at launch and then about once a day;
   `[updates] install = true|false` — additionally download found updates in the background and
   install them when QuickTerm quits (`install` implies `check`).
2. When an update is found and `install` is off: an icon in the status bar's right cluster; a click
   opens a window with version, size, date and the release notes in the UI language, with
   **Install and Relaunch** / **Later** / **Skip This Version**.
3. When `install` is on: the download runs unattended; once staged, the icon says "quit or restart
   to finish"; a click offers **Restart Now** / **Later**. Quitting installs it without relaunch.
4. **QuickTerm ▸ Check for Updates…** in the app menu; the engine's `check_for_updates` keybind
   action reaches the same entry point (today a no-op stub).
5. Every update is verified by Sparkle: the EdDSA signature over the DMG (verified before the
   image is even mounted, `SUVerifyUpdateBeforeExtraction`) plus a valid Apple code signature on
   the new bundle. Sparkle allows one of the two identities to change per update, never both.

Non-goals (this round)

- A pre-release / "tip" channel. One feed, tagged releases only.
- Exposing update state on the control plane (`quickterm` CLI / MCP) or in the notice centre.
- Delta updates. Full DMG every time (≈80 MB).
- Migrating users on ≤ 1.6.7: those builds have no updater and install the first updater-enabled
  release by hand once. The README's Install section says so.

## 2. Architecture

```
GitHub Release v<ver> (draft until complete)          QuickTerm.app
  QuickTerm-<ver>.dmg  ◄── enclosure ───────────────  Sparkle.framework (SPUUpdater)
  QuickTerm-<ver>.dmg.sha256                              │  SPUUserDriver + SPUUpdaterDelegate
  QuickTerm-<ver>-notes.md / -notes.zh-CN.md ◄── notes ── UpdateDriver (Sources/Update/)
  appcast.xml  ◄── SUFeedURL = releases/latest/download/appcast.xml   │ mirrors callbacks into
                                                       UpdateViewModel (@Published state)
                                                          │ observed by
                                          StatusBarView.rightSection ► UpdateIndicator
                                          click ► UpdateSheet (NSAlert, house style)
                                          MainMenu "Check for Updates…" ► UpdateController
                                          AppSession.applyGlobalConfig ► UpdateSettings ► flags
```

New area `Sources/Update/` with its own `Update.strings` table (keys `update.*`):

| File | Origin | Role |
|---|---|---|
| `UpdateController.swift` | Ghostty `UpdateController.swift`, adapted | Owns `updater: SPUUpdater?` (nil when disabled, §8), `start()`, `checkForUpdates()`, `installUpdate()` (Ghostty's "confirm through every installable state" chain), `apply(UpdateSettings)`, the stored `settings`, `relaunchRequested` (§4), `canCheckForUpdates`, the 5 s auto-clear timer for `notFound` (id-guarded, like `WorkspaceModel.showControlFlash`). |
| `UpdateDriver.swift` | Ghostty `UpdateDriver.swift` + `UpdateDelegate.swift`, adapted | Every `SPUUserDriver` callback mirrored into the view model, plus `SPUUpdaterDelegate` (`feedURLString`, `willInstallUpdateOnQuit`, `updaterShouldRelaunchApplication`, `updaterWillRelaunchApplication`). Ghostty's `SPUStandardUserDriver` fallback and its `TerminalWindow` / `QuickTerminalWindow` observers are deleted. `showUpdateInFocus` is implemented (opens or raises the sheet); without it Sparkle keeps `canCheckForUpdates` false while an update is on screen. |
| `UpdateViewModel.swift` | Ghostty `UpdateViewModel.swift`, adapted | `enum UpdateState` (idle, checking, updateAvailable, downloading, extracting, installing, notFound, error) carrying the Sparkle reply blocks **and** `SPUUserUpdateState` (`stage`, `userInitiated`) where Sparkle supplies it. Holds raw values only (display version, byte count, progress, date, error); no user-facing text. |
| `UpdateSettings.swift` | new | Value type from `ConfigStore.Settings`: `check`, `install`, `checksEnabled = check || install`. |
| `UpdateIndicator.swift` | new (replaces Ghostty's `UpdatePill` / `UpdateBadge`) | The status-bar item: one SF Symbol (or the progress ring) per state in the bar's monochrome style, hidden when idle; text via the `i18n` environment object at render time. |
| `UpdateSheet.swift` | new (replaces Ghostty's `UpdatePopoverView`) | Owns at most one `NSAlert`; presents per state (§4), dismisses on state transitions through a `$state` sink, text via `L()` at presentation time. |
| `ReleaseNotes.swift` | new | Fetches the notes asset for a version in the UI language and reduces Markdown to plain text. |
| `UpdateSimulator.swift` | Ghostty `UpdateSimulator.swift`, adapted | Scripted state sequences (happy path, not found, error, slow download, cancel, staged install, auto update) to exercise the UI without a server; Debug builds and tests only. |

Ownership and threading: `AppDelegate` creates `UpdateController(enabled:)` before the
`AppSession` and hands it in; `AppSession.updates` sits next to `AppSession.stats`, so
`MainWindowController` passes `session.updates.viewModel` into `RootView` → `StatusBarView` the
way it passes `stats`. Every screen's bar shows the same state. `start()` is called at the end of
`applicationDidFinishLaunching`, after `MainMenu.install(delegate:)`; it re-applies the stored
settings (the first `applyGlobalConfig` runs inside `loadInitialConfig()`, before the updater
exists) and then, when `checksEnabled`, arms the launch check: Sparkle's own scheduler only
checks at launch when a day has passed since `SULastCheckTime`, and this check is what makes "at
launch" true and what brings the indicator back after a relaunch. It cannot go out on the next
main-queue turn — `updater.start()` opens a session of its own (the probe for a resumable
installer) and refuses a `checkForUpdatesInBackground()` sent while it runs, which the E2E run
of 2026-09-25 saw on every launch — so it waits for the first `canCheckForUpdates == true` (KVO),
hops one more turn, and then sends the check unless Sparkle has meanwhile started an overdue
check itself or one has just finished (`UpdateController.launchCheckDecision`).

Ported files keep a header naming their origin (Ghostty, MIT); `docs/porting-notes.md` records
what changed. Updater events are logged with OSLog category `updates`.

## 3. Behaviour by mode

Scheduled path (Sparkle's background check, at launch and about daily):

| `check` | `install` | Scheduled checks | Update found | Indicator | Click |
|---|---|---|---|---|---|
| false | false | none | — | — | — |
| true | false | yes | state `updateAvailable`, session held open | `arrow.down.circle` until acted on | notes + Install and Relaunch / Later / Skip This Version |
| any | true | yes, through Sparkle's automatic driver | **nothing is shown while it downloads** (that driver reports no progress); once staged, `willInstallUpdateOnQuit` → state `installing` | `power.circle` "quit or restart to finish" | Restart Now / Later |

Manual **Check for Updates…** (menu or engine action) whenever the updater exists (§8): it always
uses Sparkle's interactive driver, whatever the switches, so the states below are the interactive
ones even when `install = true`. Found → the indicator appears **and the sheet opens straight
away** (`userInitiated`); none → `notFound` for 5 s (no modal); error → `error`, and its sheet
opens too (the user is watching, §4). If an update is
already on screen (session held), Sparkle routes the manual check to `showUpdateInFocus`, which
raises the sheet. During a download or extraction the menu item stays enabled and shows that
download's sheet instead of cancelling it.

Later / Skip / Cancel semantics:

- **Later** in check-only mode closes the sheet **without replying**: the reply block is retained,
  the state stays `updateAvailable`, the icon stays. Consequences: Sparkle's session stays open, so
  scheduled checks are paused until the update is acted on or the app relaunches (the launch check
  in §2 shows it again). In `install = true` mode Later replies `.dismiss` instead, so the next
  scheduled check downloads and stages it unattended.
- **Skip This Version** replies `.skip`; Sparkle persists it (`SUSkippedMinorVersion` and
  friends) and the icon goes idle. Skip is also offered for a staged update and un-stages it.
- **Cancel** during checking / downloading / extracting calls the state's cancel block; the icon
  goes idle.
- While an update is staged, `willInstallUpdateOnQuit` returns YES, which per
  `SPUUpdaterDelegate.h` stalls the update cycle and prevents further ones: no scheduled check
  re-delivers it, Sparkle's session stays open so `canCheckForUpdates` is NO (the menu item is
  disabled and the engine action does nothing), and the indicator simply persists until the app
  quits (and installs it). Sparkle resumes a staged update only in a process that starts while
  its installer is still pending (a crash or force-quit after staging): the resume arrives as
  `showUpdateFound` with `stage == .installing`; **Later** there keeps the indicator through
  Sparkle's follow-up `dismissUpdateInstallation` (it still installs on quit), and since that
  reply block is then spent, **Restart Now** on the kept state resumes it through a fresh check
  and answers the resumed question `.install`.

Automatic-mode details: a background download that fails is silent (Sparkle's automatic driver
reports nothing); the next scheduled check retries. If `/Applications` is not writable by this user,
the automatic driver cannot stage the install (`SUInstallationAuthorizeLaterError`); the update
resurfaces on a later scheduled check as `showUpdateFound` with `stage == .downloaded`, i.e. the
interactive sheet with an "already downloaded" intro, and installing then goes through Sparkle's
authorization prompt. Install-on-quit installs **without** relaunching; the new version appears at
the next launch, where Sparkle calls `showUpdateInstalledAndRelaunched(false)` and the driver
acknowledges it (no UI).

## 4. State → indicator → sheet

| State | Icon (SF Symbol) | Colour | Tooltip / accessibility | Sheet |
|---|---|---|---|---|
| idle | hidden | — | — | — |
| checking | `arrow.triangle.2.circlepath` | foreground | Checking for updates… | title only, **Cancel**; auto-dismissed when the state changes |
| updateAvailable, `stage == .notDownloaded` | `arrow.down.circle` | accent | QuickTerm 1.6.8 is available | intro "You have 1.6.7. Version 1.6.8, 78 MB, released 2026-09-30." + notes; **Install and Relaunch** / **Later** / **Skip This Version**; link "View on GitHub" |
| updateAvailable, `stage == .downloaded` | `arrow.down.circle` | accent | QuickTerm 1.6.8 is downloaded | intro "Version 1.6.8 is already downloaded."; same buttons |
| downloading (interactive path only) | progress ring 0–100 % | accent | Downloading 1.6.8: 42 % | progress + **Cancel** |
| extracting (interactive path only) | progress ring | accent | Preparing 1.6.8… | progress, **OK** only closes the sheet |
| installing (staged, or `showUpdateFound` with `stage == .installing`) | `power.circle` | accent | Quit or restart to finish updating to 1.6.8 | **Restart Now** / **Later** / **Skip This Version** |
| notFound | `checkmark.circle` for 5 s | foreground | You're up to date | none |
| error, translocated (§8) | `exclamationmark.triangle` | alert | Update failed | message, **OK** (no Retry) |
| error, other | `exclamationmark.triangle` | alert | Update failed | message + **Retry** / **OK** |

Rules

- The indicator is the **leftmost** item of `rightSection` (left of the CPU figure), so the four
  system items keep their positions when it appears and disappears; Monaco 12, monochrome,
  26 pt bar. The ring uses the bar's stroke widths (Ghostty's `UpdateBadge` scaled). The header
  comments of `StatusBarView.swift` and `WorkspacePill.swift` list it.
- Sparkle reply and acknowledgement blocks are always answered by the driver / controller, never
  by a view: `showUpdateNotFoundWithError`, `showUpdaterError` and
  `showUpdateInstalledAndRelaunched` acknowledge **immediately** (the session ends; the bar may be
  hidden, and there is one bar per screen), and the "up to date" / error display is QuickTerm's own
  state — cleared by the 5 s timer or a click, or by **OK** / **Retry**; `dismissUpdateInstallation`
  clears everything to idle.
- The sheet is the house info window (`NSAlert`, `setScrollableBody(_:intro:)` only for states with
  a body), attached to the key window when there is one (`beginSheetModal`) and `runModal`
  otherwise. `UpdateSheet` keeps a `$state` sink: any transition ends the current sheet
  (`window.endSheet` / `NSApp.abortModal`); the new state re-presents only if it is one the user
  asked to see (a manual check, a click) or `updateAvailable` arriving from a manual check.
  While a download runs the sheet is closed and progress lives on the icon; a click reopens it.
- **Install and Relaunch** routes through `updateController.installUpdate()`, which starts the
  download; **Restart Now** sets `relaunchRequested` and then invokes Sparkle's immediate-install
  block. `relaunchRequested = true` means Sparkle is about to terminate the app, so only Restart
  Now, `showReady` (whose reply is `.install`) and `showInstallingUpdate` set it; the Install
  click does not, and the user's own Cmd+Q during the download still asks about open panes.
  Dismiss, skip, cancel and error clear it. Sparkle terminates the app with an ordinary quit
  event, so this flag is what `applicationShouldTerminate` consults (§8). If the user still
  cancels the quit, Sparkle calls `showInstallingUpdate(withApplicationTerminated: false, retry:)`;
  the state stays `installing` and the sheet's **Restart Now** calls the retry block.
- After the app quits on Install and Relaunch, Sparkle's own small progress window ("Updating…",
  Sparkle-localized) may appear while files are copied. Accepted: it only exists while QuickTerm is
  not running.

## 5. Configuration

New section `[updates]` (title EN "Updates" / ZH "更新"), inserted after `[notifications]` and
before `[keybinds]` in `ConfigSection`:

```toml
[updates]
# check = true
# install = false
```

| Key | Kind | Default | Meaning (help text, EN) |
|---|---|---|---|
| `check` | bool | true | Check GitHub Releases for a newer QuickTerm at launch and about once a day. `install = true` checks even when this is off. |
| `install` | bool | false | Download a found update in the background and install it when QuickTerm quits. Implies `check`. |

Rules

- Both keys hot-reload: `AppSession.applyGlobalConfig` builds `UpdateSettings(settings)` and calls
  `updates.apply(_:)`, which stores it and, when the updater exists, writes
  `automaticallyChecksForUpdates = checksEnabled` **first** and then
  `automaticallyDownloadsUpdates = install` (Sparkle ignores the second while the first is false).
  No explicit `resetUpdateCycle`: Sparkle resets itself on the checks flag change, and calling it
  before `start()` only logs an error. The config is the source of truth over Sparkle's persisted
  preferences: the flags are written on every apply.
- `Info.plist` (via `project.yml` `info.properties`): `SUFeedURL`, `SUPublicEDKey`,
  `SUEnableAutomaticChecks = true` (Sparkle never shows its second-launch permission prompt),
  `SUVerifyUpdateBeforeExtraction = true`. `SUScheduledCheckInterval` stays at Sparkle's 86400 s.
  The permission-request callback is still implemented: it replies from the current settings
  (`automaticUpdateChecks = checksEnabled`, `sendSystemProfile = false`) without UI.
- Sparkle owns these keys in the `dev.danny.quickterm` defaults domain: `SUEnableAutomaticChecks`,
  `SUAutomaticallyUpdate`, `SULastCheckTime`, `SUHasLaunchedBefore`, `SUSkippedMinorVersion`
  (and Major variants). The config overwrites the first two on every apply. Dev recipe:
  `defaults delete dev.danny.quickterm SULastCheckTime` forces the next scheduled check.
- The engine's `auto-update` / `auto-update-channel` keys (parsed by `Ghostty.Config`, ignored
  today) stay ignored; a sentence under the READMEs' engine-configuration section and the
  `[ghostty]` template note say so.
- ZH/EN label and help pairs in `ConfigSchema`, `Settings` fields `updatesCheck` /
  `updatesInstall`, bindings `updates.check` / `updates.install`, template lines and the
  `[updates]` block in both READMEs (`testEveryKeyIsDocumented`). No cross-key validation in the
  schema; `UpdateSettings` derives `checksEnabled`.

## 6. Release notes

- Source of truth: `docs/releases/v<ver>.md` (English) and `docs/releases/v<ver>.zh-CN.md`
  (Chinese), both required for every release from now on (§7 preflight). The English file remains
  the GitHub release body.
- Delivery: `make-release.sh` uploads both files as release assets, `QuickTerm-<ver>-notes.md` and
  `QuickTerm-<ver>-notes.zh-CN.md`, next to the DMG. They are therefore fetched from the same host
  as the update itself (`github.com/…/releases/download/v<ver>/…`), not from
  raw.githubusercontent.com, which is unreachable for some of the Chinese-UI users.
- The sheet fetches the asset for the UI language (`[general] language` resolved by
  `Localization`), falling back to the other language, then to the appcast item's `<description>`
  (English), then to the GitHub release link alone. The fetch is asynchronous with a 10 s timeout;
  the body says "Loading release notes…" until it lands and a failure never blocks the buttons.
  Cached per version for the process lifetime. The version in the URL is
  `SUAppcastItem.displayVersionString`, validated against `^\d+\.\d+\.\d+$` before use.
- Rendering: Markdown reduced to plain text for the house text area — heading markers dropped
  (heading text kept on its own line), `- ` list markers turned into `• `, inline code / emphasis
  markers stripped, `[text](url)` shown as `text (url)`, fenced code kept verbatim. No web view.
  The appcast fallback text goes through the same reducer.
- The appcast item carries the English notes' Markdown source in `<description
  sparkle:descriptionFormat="plain-text">` (`SUAppcastItem.h` of 2.10 documents only `html` and
  `plain-text`; QuickTerm's own driver flattens the Markdown, nothing else renders it) and
  `<sparkle:fullReleaseNotesLink>` to the GitHub release page; `sparkle:releaseNotesLink` is
  deliberately absent, so `showUpdateReleaseNotes` is never called and stays a no-op.

## 7. Release pipeline

One-time setup (user, on the release Mac)

1. Run Sparkle's `generate_keys` once. The private key lands in the login Keychain; the printed
   public key goes into `project.yml` → `info.properties.SUPublicEDKey`. Immediately export a backup
   with `generate_keys -x <file>` to offline storage (`generate_keys -f <file>` imports it on a
   replacement Mac); losing the key forces a key-rotation release signed under the same Developer
   ID.
2. Run `sign_update` once by hand on any file and answer the Keychain prompt with "Always Allow", so
   `make-release.sh` never blocks on it. The script needs a GUI login session.

Dependency pinning

- `project.yml` gains `packages: Sparkle: url: https://github.com/sparkle-project/Sparkle,
  exactVersion: 2.10.0`; the QuickTerm target links the `Sparkle` product (the implementer picks
  `embed:` so that exactly one `Contents/Frameworks/Sparkle.framework` ends up in the app; Xcode
  embeds SwiftPM binary products on its own) and the test target links it too (`@testable import`
  exposes Sparkle types). `QuickTerm.xcodeproj/` is git-ignored, so `Package.resolved` is not
  committed; the exact version is the pin. Bumps are deliberate edits.
- `make-release.sh` carries `SPARKLE_VERSION=2.10.0` and `SPARKLE_SHA256` (the checksum from
  Sparkle's `Package.swift` for that tag). It locates `sign_update` / `generate_keys` with
  `find "$DERIVED/SourcePackages/artifacts" -type f -name sign_update -perm -u+x`, else downloads
  `Sparkle-for-Swift-Package-Manager.zip` of that version into `.tools/`, verifies the checksum
  before unzipping, and asserts the embedded framework's `CFBundleShortVersionString` equals
  `SPARKLE_VERSION`. `xcodebuild` now fetches the Sparkle binary package (proxy note in the README
  next to the Zig one).

Per release (`scripts/make-release.sh`)

0. Preflight (before the 10-minute build): `--upload` requires `--notarize`; `SUPublicEDKey` and
   `SUFeedURL` present and non-empty in the source `project.yml`; `generate_keys -p` output equals
   `SUPublicEDKey`; `sign_update` on a scratch file succeeds (Keychain unlocked); with `--upload`,
   `git cat-file -e "$TAG:docs/releases/$TAG.md"` and `"$TAG:docs/releases/$TAG.zh-CN.md"` both
   succeed (the notes are in the tag) — no `--generate-notes` fallback any more; the built
   `CFBundleVersion` is strictly greater than every `sparkle:version` in the previous appcast
   (and than 23 on the first release), and no existing item has the same
   `CFBundleShortVersionString` with a different build number.
1. Signing: after the existing file loop (SharedSupport / Helpers) and before the app, sign
   Sparkle's nested code **by bundle path, inside-out**, each with
   `codesign --force --options runtime --timestamp --preserve-metadata=entitlements --sign "$IDENTITY"`
   and an `[ -e ]` guard so a layout change fails loudly:
   `Sparkle.framework/Versions/B/XPCServices/Downloader.xpc`, `…/Installer.xpc`,
   `Versions/B/Autoupdate`, `Versions/B/Updater.app`, then `Sparkle.framework` itself. Never
   `--deep`. The unsandboxed app does not use the XPC services, but notarization requires them
   signed. `codesign --verify --deep --strict` stays as the gate.
2. After the DMG is notarized and stapled: `sign_update QuickTerm-<ver>.dmg` → parse
   `sparkle:edSignature="…" length="…"`.
3. `scripts/update-appcast.py` builds `build/appcast.xml` with ElementTree (no CDATA, proper
   escaping): fetch the existing feed from the **previous release's** assets
   (`gh release list` → previous tag → `releases/download/<prev>/appcast.xml`), or accept its
   absence only with `--first-release`; refuse a `sparkle:version` that is not greater than every
   existing one; prepend the new item — `sparkle:version` = `CFBundleVersion`,
   `sparkle:shortVersionString` = `CFBundleShortVersionString`, `sparkle:minimumSystemVersion` =
   the built app's `LSMinimumSystemVersion` (three components), `pubDate` in Sparkle's only
   accepted shape `E, dd MMM yyyy HH:mm:ss Z` (en_US), the English notes as `<description>`
   (plain-text, §6), `<sparkle:fullReleaseNotesLink>`, `<enclosure url="https://github.com/dannyzhu/QuickTerm/releases/download/v<ver>/QuickTerm-<ver>.dmg" length=… type="application/x-apple-diskimage" sparkle:edSignature=…>` —
   keep the newest 15 items, sorted tolerantly (document order when a `pubDate` fails to parse).
   Then verify the DMG against the item (signature, length) before anything is uploaded.
4. `--upload`: create the release **as a draft** with the DMG, `.sha256`, both notes assets and
   `appcast.xml`, then `gh release edit --draft=false`. Drafts are excluded from `latest`, so the
   feed URL switches atomically and never points at a release without its appcast. An existing
   release for the tag is updated with `--clobber` for all five assets, and one that is still a
   draft (an interrupted publish) is then published. After publishing, `curl -fsSL` the live feed
   and assert it contains the new `sparkle:version`, `length` and `sparkle:edSignature`, retrying
   six times 10 s apart for GitHub's redirect to catch up (fail loudly otherwise).
5. Without `--upload` the appcast is written locally only, so the dry run exercises the same code
   path.

Feed URL: `https://github.com/dannyzhu/QuickTerm/releases/latest/download/appcast.xml` (verified to
redirect to the latest release's asset; pre-releases and drafts are excluded).

Operational rules (README "Releasing" / memory):

- Every DMG handed to anyone, test builds included, gets its own higher `CURRENT_PROJECT_VERSION`;
  the script enforces "strictly greater" against the feed.
- Rollback happens by itself: deleting the latest release makes `latest` fall back to the
  previous one, and since each release's appcast is its predecessor's plus its own item, that
  appcast never advertised the deleted DMG.
- Any release made by hand without `appcast.xml` breaks the feed for every client until fixed;
  releases are made with the script.
- Checklist: bump `MARKETING_VERSION` and `CURRENT_PROJECT_VERSION`, write both notes files,
  commit, tag, push the tag, `make-release.sh --notarize --upload` (plus `--first-release` for the
  first updater release only: 1.6.7 has no appcast to build on).

## 8. Security and edge cases

- Trust: TLS to GitHub + EdDSA signature over the DMG, verified before extraction, + Sparkle's
  Apple code-signing check of the new bundle. A feed compromise alone cannot ship an update.
- The updater exists only when all hold: not the test host (`AppDelegate.isRunningTests`),
  `SUPublicEDKey` present and non-empty, and (Release build, or Debug build with the feed override
  set). Otherwise `updater` is nil: `canCheckForUpdates` is false (menu item disabled through the
  existing `validateMenuItem` switch in `AppDelegate+Screens.swift`), the engine action is a no-op,
  `apply` only stores settings, the view model stays idle. A Release-configuration app under
  `build/` behaves like the shipped app (it carries the real feed URL); a Debug app in DerivedData
  is never replaced by a release DMG.
- Feed override: a fourth `LaunchOverrides` switch, `--update-feed-url` /
  `QUICKTERM_UPDATE_FEED_URL`, honoured only where `UpdateController.allowsFeedOverride` is
  compiled true, `#if DEBUG || UPDATE_E2E`: Debug builds (xcodegen sets
  `SWIFT_ACTIVE_COMPILATION_CONDITIONS = DEBUG` for Debug) and the end-to-end test's Release
  builds, to which `make-release.sh` adds `UPDATE_E2E` whenever `E2E_BUNDLE_ID` or
  `E2E_BUILD_NUMBER` is set (§11). Those are never uploaded, so a shipped release always reads
  `SUFeedURL`. `updaterShouldRelaunchApplication` always returns true: in Sparkle 2 a NO there
  is consulted by `SPUInstallerDriver.mayUpdateAndRestart` before stage 2 and aborts the whole
  installation (the E2E run of 2026-09-25 found the app idle with the installer left waiting),
  so it cannot mean "install without relaunching". Sparkle's relaunch carries neither arguments
  nor environment, which would produce an unmarked primary instance on the user's real config,
  socket and `state.json`; the E2E build therefore keeps its launch overrides in its own
  defaults domain (`LaunchOverrides.reconciled(with:)`, `UPDATE_E2E` only): a launch that names
  any override stores the set, a launch that names none takes it back, so the relaunched
  instance keeps its scratch locations. The tear-down's `defaults delete` wipes it.
- App Translocation / read-only volume: Sparkle itself refuses to check in those two cases
  (`SURunningTranslocated`, `SURunningFromDiskImageError`) — silently for scheduled checks, and
  through `showUpdaterError` for a manual one. The driver maps those two codes to the sheet "Move
  QuickTerm to the Applications folder to update" with **OK** only. No home-grown path check: an
  unwritable-but-writable-by-admin `/Applications` is Sparkle's authorization path, not an error.
- Quit path: `AppDelegate.shouldConfirmQuit(openPaneCount:relaunchRequested:)` returns false when
  a relaunch was requested (§4), so `applicationShouldTerminate` returns `.terminateNow` without
  the "N panes open" alert; `applicationWillTerminate` still runs and writes the session to
  `state.json` synchronously as on any quit. `updaterWillRelaunchApplication` invalidates AppKit's
  restorable state as Ghostty does; QuickTerm's own session restore brings the layout back.
- Skipped versions, last-check time and the two automatic flags live in the app's defaults domain;
  E2E runs use a different bundle identifier (§11) so nothing leaks into the installed app.
- The `quickterm` CLI symlink points into the bundle; Sparkle replaces the bundle at the same path,
  so the link survives.
- Network use: Sparkle's feed and enclosure requests, the notes asset fetch; no token, no
  telemetry.

End to end (before the first updater-enabled release; the user's real QuickTerm may keep running)

- Both apps are Release builds made by `make-release.sh` (never with `--upload`, which the E2E
  variables refuse) with `E2E_BUNDLE_ID=dev.danny.quickterm.e2e` and `E2E_BUILD_NUMBER=9001` /
  `9002`. The script passes them to `xcodebuild` (`PRODUCT_BUNDLE_IDENTIFIER`,
  `CURRENT_PROJECT_VERSION`) and adds the `UPDATE_E2E` compilation condition, so these builds go
  through the real signing and appcast path and still honour `--update-feed-url` (§8). Build
  numbers in the 9000s are never released.
- The 9002 run's DMG and the appcast it wrote (with `--first-release`; its enclosure URL edited
  to point at the pre-release asset) are attached by hand to a temporary **pre-release**
  (`e2e-<date>`, excluded from `latest`), on a private scratch repository if the user prefers;
  the feed is therefore served over https with no ATS exception. Deleted afterwards.
- The 9001 app is copied out of `build/` before the second build wipes it, into `/Applications`
  under its own name (`/Applications/QuickTerm E2E.app`, never over the installed QuickTerm), so
  it runs untranslocated from a writable place Sparkle can replace in place. It is launched with
  `--update-feed-url <…/releases/download/e2e-<date>/appcast.xml>`, `--state-file`,
  `--control-socket` and `--config-file` pointing at scratch locations; walk: check → indicator
  → sheet → Install and Relaunch → the app quits and Sparkle relaunches it; the relaunched
  instance takes its overrides back from its defaults domain (§8) → the newer app (build 9002)
  comes back with the scratch layout restored. Repeat with `install = true` for the staged-on-quit path (Restart Now
  and plain quit). The first run also answers whether Sparkle's Gatekeeper scan accepts the
  unnotarized e2e DMG; if not, notarize the e2e DMG as well.
- Teardown: `defaults delete dev.danny.quickterm.e2e`, delete the pre-release,
  `/Applications/QuickTerm E2E.app` and the scratch files.
- `make-release.sh` dry run (no `--upload`) produces `build/appcast.xml` that validates against
  the DMG's signature and size.
